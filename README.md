# Images Hosting

Cервіс для завантаження, перегляду та видалення зображень з пагінацією і резервним копіюванням бази даних.

Проєкт складається з трьох контейнерів: **Nginx** (точка входу), **Python-бекенд** (`http.server`) та **PostgreSQL** (метадані зображень).

## Можливості

- Завантаження зображень (`jpg`, `png`, `gif`) розміром до 5 МБ.
- Збереження файлів у папці `images/`, метаданих (ім'я, розмір, тип, дата) у PostgreSQL.
- Список зображень із пагінацією (10 записів на сторінці).
- Відкриття зображення за кліком на 📂, видалення за кліком на 🗑 (файл і запис у БД).
- Резервне копіювання БД через `pg_dump` (лінк **Create Backup**).
- Логування в `logs/app.log`.

## Архітектура

```
Користувач ──► nginx :8080 ──┬─► /images/*  → файли з папки images (напряму)
                             └─► усе інше   → app:8000 (Python) ──► db:5432 (PostgreSQL)
```

| Сервіс  | Образ / збірка        | Порт                                  | Призначення                              |
|---------|-----------------------|---------------------------------------|------------------------------------------|
| `nginx` | `nginx:alpine`        | `8080` (зовнішній)                    | Віддає зображення, проксує решту на `app` |
| `app`   | збірка з `Dockerfile` | `8000` (лише всередині мережі Docker) | Python-бекенд                            |
| `db`    | `postgres:18-alpine`  | `5432` (не публікується)              | Зберігання метаданих                     |

## Структура проєкту

```
.
├── app.py                 # Python-бекенд
├── Dockerfile             # образ для app
├── docker-compose.yml     # опис сервісів
├── nginx.conf             # конфіг nginx (монтується як conf.d/default.conf)
├── requirements.txt       # залежності Python (psycopg[binary])
├── backup.sh              # ручне створення резервної копії
├── .env                   # змінні оточення (не комітити!)
├── static/
│   ├── index.html         # сторінка завантаження
│   ├── images-list.html   # шаблон списку зображень
│   └── style.css
├── images/                # завантажені зображення (том)
├── logs/                  # app.log (том)
└── backups/               # резервні копії БД (том)
```

## Вимоги

- Docker та Docker Compose v2
- Для `backup.sh`: bash (Linux/macOS/WSL/Git Bash)

## Налаштування

Створіть файл `.env` у корені проєкту:

```dotenv
POSTGRES_USER=images_backend
POSTGRES_PASSWORD=change_me
POSTGRES_DB=images_hosting
DB_HOST=db
DB_PORT=5432
```

Додайте до `.gitignore` та `.dockerignore`:

```
.env
images
logs
backups
```

### Змінні оточення застосунку

| Змінна                                                               | За замовчуванням | Опис                       |
|----------------------------------------------------------------------|------------------|----------------------------|
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `DB_HOST`, `DB_PORT` | —          | Параметри підключення до БД (обов'язкові) |
| `LOG_DIR`                                                            | `logs`           | Папка для `app.log`        |
| `BACKUP_DIR`                                                         | `/backups`       | Папка для резервних копій  |

## Запуск

```bash
mkdir -p images logs backups
docker compose up -d --build
```

Після запуску:

- Завантаження зображень: <http://localhost:8080/>
- Список зображень: <http://localhost:8080/images-list>

Зупинка:

```bash
docker compose down        # зупинити, дані БД зберігаються
docker compose down -v     # УВАГА: також видаляє том БД (усі записи)
```

## Маршрути

| Метод | Шлях                 | Опис                                              |
|-------|----------------------|---------------------------------------------------|
| GET   | `/`                  | Сторінка завантаження                             |
| POST  | `/`                  | Завантаження зображення (multipart/form-data)     |
| GET   | `/images-list?page=N`| Список зображень, сторінка `N` (10 на сторінці)   |
| GET   | `/images/<filename>` | Зображення (віддає nginx з папки `images`)        |
| GET   | `/delete-image/<id>` | Видалення зображення та запису в БД               |
| GET   | `/backup`            | Створення резервної копії БД (кнопка Create Backup) |
| GET   | `/static/<file>`     | Статичні файли (CSS тощо)                         |

## Дані та томи

| Що                  | Де в контейнері            | Де на хості   |
|---------------------|----------------------------|---------------|
| Зображення          | `/app/images` (app), nginx — лише читання | `./images` |
| Логи                | `/logs`                    | `./logs`      |
| Резервні копії      | `/backups`                 | `./backups`   |
| Дані PostgreSQL     | `/var/lib/postgresql`      | іменований том `db_data` |

> Для `postgres:18` і новіших том монтується в `/var/lib/postgresql`, а не в `/var/lib/postgresql/data`.

## Пагінація

Список на `/images-list` показує по 10 записів, відсортованих за `id`. Номер сторінки передається параметром `?page=N`. Некоректні значення (`abc`, `0`, більше за кількість сторінок) приводяться до допустимих.

## Резервне копіювання БД

Копії створюються за допомогою `pg_dump` і зберігаються у `./backups` з іменем у форматі `backup_YYYY-MM-DD_HHMMSS.sql`, наприклад `backup_2026-10-07_153000.sql`.

### Спосіб 1: команда вручну

```bash
chmod +x backup.sh
./backup.sh
```

Скрипт читає `POSTGRES_USER` і `POSTGRES_DB` з `.env` та виконує `docker exec db pg_dump ...`.

Еквівалент без скрипта:

```bash
docker exec db pg_dump -U images_backend images_hosting > backups/backup_$(date +%Y-%m-%d_%H%M%S).sql
```

> Не додавайте прапорець `-t` до `docker exec` при перенаправленні у файл: псевдотермінал додає символи `\r` і може пошкодити дамп.

### Спосіб 2: кнопка в інтерфейсі

На сторінці `/images-list` натисніть **Create Backup**. Бекенд сам викликає `pg_dump` (клієнт PostgreSQL встановлено в образі `app`) і зберігає файл у `/backups`.

### Відновлення

```bash
docker exec -i db psql -U images_backend -d images_hosting < backups/backup_2026-10-07_153000.sql
```

Якщо таблиця `images` уже існує, спершу очистіть її або створіть базу заново, інакше команда видасть помилки про існуючі об'єкти.

> Резервні копії містять лише базу даних. Самі зображення лежать у `./images`, їх варто копіювати окремо.

## Діагностика

| Симптом                                          | Що перевірити                                                                 |
|--------------------------------------------------|-------------------------------------------------------------------------------|
| `KeyError: 'POSTGRES_PASSWORD'` у логах app      | У сервісі `app` має бути `env_file: .env`                                     |
| Застосунок не підключається до БД                | `docker compose logs app`, `logs/app.log`; змінні `DB_HOST=db`, `DB_PORT=5432` |
| `413 Request Entity Too Large`                   | У `nginx.conf` має бути `client_max_body_size 6m;`                            |
| Зображення не відкривається                      | Чи змонтовано `./images` в обидва контейнери; `docker compose exec app ls /app/images` |
| Файли не з'являються в `./images` на хості       | Чи на порту 8080 справжній nginx: `docker compose exec nginx nginx -v`        |
| Після перестворення контейнерів зникли записи    | Чи підключено том `db_data`; не використовуйте `down -v`                      |
| `No such file or directory: 'pg_dump'`           | Перезберіть образ: `docker compose build --no-cache app`                      |
| `server version mismatch` при бекапі             | Версія клієнта `pg_dump` має бути не нижчою за версію сервера (18)            |

Корисні команди:

```bash
docker compose ps
docker compose logs -f app nginx
tail -f logs/app.log
docker compose exec nginx nginx -t
```

## Відомі обмеження

- Видалення та створення резервної копії виконуються через GET-запити. Для локального проєкту це допустимо, а для публічного розгортання варто перейти на POST і додати авторизацію.
- Multipart-запити розбираються вручну, тому підтримується завантаження одного файла за запит. Для розширення функціональності краще використати готову бібліотеку або фреймворк.
- Тип файлу визначається за розширенням, вміст не перевіряється.
- Сервер працює в одному потоці (`HTTPServer`) з одним з'єднанням до БД, тож не призначений для високого навантаження.
- Пароль БД зберігається в `.env`: не додавайте його до системи контролю версій.
